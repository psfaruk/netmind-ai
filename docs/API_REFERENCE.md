# API Reference — `/api/v1`

> Status: **Implemented & Tested**: `/auth`, `/models`, `/nodes`, `/tasks`, `/workers` (Phase 2 execution engine), `/monitoring`. **Documented placeholders (501)**: `/agents`, `/knowledge`, `/research`, `/compute`, `/feedback` — each returns `{"detail": "Planned for Phase N", "phase": N}`; they exist so the API surface is explicit, not to fake behavior.

Base URL: `http://<host>:8000` · Interactive docs: `/docs` (OpenAPI 3.1, generated by FastAPI).

## 1. Conventions

- **Auth:** `Authorization: Bearer <jwt>` (user) or `X-API-Key: <key>`. JWTs expire in 30 min; API keys are long-lived and revocable.
- **Errors:** RFC-7807-style body: `{"detail": "...", "error_code": "...", "request_id": "..."}`.
- **Rate limits:** token bucket per key; default 60 req/min; `429` with `Retry-After`.
- **Validation:** Pydantic rejects invalid payloads with `422` + field-level details.
- **Async:** long operations return `202` + task id immediately; status via `GET /tasks/{id}`.
- **Streaming:** final responses stream via SSE (Phase 2+, `text/event-stream`).
- **Versioning:** URL-versioned (`/api/v1`); breaking changes ⇒ `/api/v2`.

## 3. Authentication — `/api/v1/auth`

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | — | create user (email, password ≥8 chars) |
| POST | `/auth/login` | — | obtain JWT |
| GET | `/auth/me` | JWT | current user profile |
| POST | `/auth/api-keys` | JWT | create API key (returns plaintext once) |
| GET | `/auth/api-keys` | JWT | list keys (hashed) |

Example:

```bash
curl -X POST http://localhost:8000/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email": "owner@example.com", "password": "correct-horse", "display_name": "Owner"}'
# → 201 {"id": "...", "email": "owner@example.com"}

curl -X POST http://localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email": "owner@example.com", "password": "correct-horse"}'
# → 200 {"access_token": "eyJ...", "token_type": "bearer", "expires_in": 1800}
```

## 4. Models — `/api/v1/models`

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/models` | key/JWT | list registry (filter `capability`, `language`) |
| GET | `/models/{id}` | key/JWT | one registry record |
| POST | `/models` | JWT (admin) | add registry record (license + memory required) |

Registry rows are metadata only — `availability=true` requires a verified runtime (see `AI_MODEL_REGISTRY.md`); the list endpoint marks `availability` per row so callers can see what is actually deployable.

## 5. Nodes — `/api/v1/nodes`

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/nodes/register` | key/JWT | register node: `node_id` (Ed25519 pubkey), capabilities {cpu_cores, ram_mb, gpu, runtimes[], region, contribution_limits} |
| POST | `/nodes/{node_id}/heartbeat` | node | workload/health ping (30 s cadence) |
| GET | `/nodes` | key/JWT | list nodes (public fields only — no sensitive device data) |
| PATCH | `/nodes/{node_id}` | node owner | availability, contribution limits |

Node listings never expose device-identifying detail beyond coarse region and capability class (master prompt §3).

## 6. Tasks — `/api/v1/tasks`

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/tasks` | key/JWT | submit request `{ "kind": "chat|research|coding|math|translation|vision", "input": {...}, "priority": 1-9, "deadline_sec": int?, "model_id": "registry-id"? }` → `202 {task_id, status:"queued", model_id, note}` — routed to a registry model; the note states a worker must claim it before any inference runs |
| GET | `/tasks/{task_id}` | owner | status + result (when complete) — result carries `output, backend, model_id, tokens, duration_ms` |
| POST | `/tasks/{task_id}/cancel` | owner | cancel → `CANCELLED` |
| GET | `/tasks` | owner | own task history (paginated) |

Phase 2 truth-in-advertising: creation routes the task and queues it; execution happens when a worker advertising that model claims it — nothing pretends to have run.

## 6b. Workers — `/api/v1/workers` (Phase 2)

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/workers/claim` | key/JWT (node owner) | claim next queued task: `{node_id, models[]}` → `{accepted, task | null, requeued}` — priority then FIFO; expired claims are requeued first (TTL 120 s, max 3 attempts) |
| POST | `/workers/results` | key/JWT (node owner) | submit outcome: `{task_id, node_id, status: completed|failed, result, error?}` → `{task_id, status}` — late results for expired claims rejected `409` |

Interim auth: workers authenticate with the node owner's API key; node-signed envelopes (Ed25519) arrive Phase 5 (see `NETWORK_PROTOCOL.md`). Full design in `PHASE2_EXECUTION_ENGINE.md`.

## 7. Monitoring — `/api/v1/monitoring`

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/monitoring/stats` | key/JWT | counts: users, nodes (by state), models (available vs total), tasks (by state) |

Root-level: `GET /health` (liveness), `GET /ready` (DB probe) — unauthenticated by design.

## 8. Change Policy

Endpoint additions are backward-compatible; removals/renames only at a new major version. Every endpoint keeps: request validation, response schema, auth rules, error handling, rate limiting where required, and `/docs` coverage (charter §13).
